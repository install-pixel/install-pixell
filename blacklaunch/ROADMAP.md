# BlackLaunch — Roadmap (адаптована версія 1.1)

Основа: «BlackLaunch — головний roadmap проєкту», версія 1.0.
Ця версія зберігає мету, обсяг, модель даних і правила оригіналу та адаптує їх
під наш реальний процес роботи. Усі відхилення від версії 1.0 перелічено в розділі 3.

**Фінальне правило:** одна ціль → один етап → перевірка → фіксація результату → наступний етап.

---

## 1. Мета (без змін)

Власний домашній екран Android: чорний екран, пошук програм українською та
англійською (текстом і голосом), профілі «Робота», «Дім», «Відпочинок» із власними
закріпленими програмами, режимом звуку та правилами «Не турбувати». Усе зберігається
локально. Стандартний лаунчер завжди можна повернути.

BlackLaunch керує тільки власним інтерфейсом і тими системними параметрами, які
дозволяють офіційні API Android. Root, Accessibility-обходи та приховані API не використовуємо.

## 2. Як ми працюємо

| Хто | Що робить |
|---|---|
| Claude (хмарне середовище) | пише код, unit-тести, документацію; комітить і пушить у гілку |
| GitHub Actions | збирає APK, запускає unit-тести та lint, публікує APK у релізі `blacklaunch-latest` |
| Ви (телефон) | встановлюєте APK, проходите чекліст етапу, пишете результат |

Обмеження цього процесу (чесно):
- Android SDK у хмарному середовищі недоступний, тому «проєкт компілюється» означає
  «зелена збірка в GitHub Actions», а не локальна збірка.
- Емулятора немає. Усе, що стосується поведінки Android (Home, клавіатура, голос,
  звук, DND), перевіряєте ви на телефоні. Claude не позначає такі пункти виконаними без вашого звіту.
- Логіку без UI (пошук, нормалізація, псевдоніми, транслітерація, правила профілів)
  покриваємо JVM unit-тестами, їх CI запускає на кожен пуш.

Вартість: усе безкоштовно. GitHub Actions безкоштовні для публічного репозиторію,
для приватного є 2000 хвилин на місяць, а одна збірка триває приблизно 3–6 хвилин.

## 3. Що змінено порівняно з версією 1.0

1. **Розміщення.** У цьому репозиторії вже є застосунок Sklado (Flutter). BlackLaunch
   живе в окремій папці `blacklaunch/` зі своїм CI і не зачіпає Sklado.
   Пізніше можна винести його в окремий репозиторій без втрати історії.
2. **Перевірка на телефоні блоками.** Кожен етап і далі має свій коміт і свій звіт,
   але на телефоні ми перевіряємо блок етапів, щоб не ганяти APK заради кожної дрібниці:

   | Блок | Етапи | Що перевіряєте на телефоні |
   |---|---|---|
   | 0 | 0 | APK встановлюється й запускається |
   | A | 1 + 2 | Home, чорний екран, пошук дотиком і жестом, клавіатура, Back |
   | B | 3 + 4 + 5 | список програм, запуск, пошук укр/англ, псевдоніми |
   | C | 6 + 6a + 6b | голос, команди «відкрий останній», історія |
   | D | 7 + 8 + 8a + 8b | профілі, швидке перемикання, розумний і глобальний пошук |
   | E | 9 + 10 | звук, «Не турбувати», дозволи |
   | F | 11 + 11a + 12a | налаштування, експорт/імпорт, опційна ШІ |
   | RC | 13 + 14 | повний прохід і реліз |

   Якщо блок не пройшов перевірку, далі не йдемо (правило 5 зберігається).
3. **LauncherApps замість «голого» PackageManager.** `LauncherApps` — офіційний API для
   лаунчерів. Він повертає саме програми з іконкою в меню, враховує робочий профіль
   Android і сам повідомляє про встановлення, видалення та оновлення програм.
   Тоді не потрібен ні `QUERY_ALL_PACKAGES`, ні власний BroadcastReceiver.
4. **Тихий режим (SILENT) залежить від доступу DND.** З Android 7 перемикати телефон
   у беззвучний режим (і з нього) можна тільки після надання доступу «Не турбувати».
   NORMAL і VIBRATE працюють без нього. Тому на Етапі 9 SILENT показується як
   «потрібен доступ», а сам доступ реалізуємо на Етапі 10.
5. **Жести.** Свайп вгору або дотик відкриває пошук. Свайп униз на лаунчерах зазвичай
   відкриває шторку сповіщень, але офіційного API для цього немає. Тому свайп униз
   у v1 нічого не робить, а ідея лежить у backlog.
6. **Голос.** Основний варіант — `SpeechRecognizer` усередині лаунчера. Якщо сервісу
   немає, запускаємо системне вікно `RecognizerIntent`. Якщо немає й нього, показуємо зрозуміле повідомлення.
7. **Підпис.** Тестові збірки підписані фіксованим ключем із репозиторію, щоб оновлення
   ставилися поверх. Реліз 1.0 підписуємо окремим ключем, який зберігається тільки
   в GitHub Secrets і у вас (Етап 14).
8. **Профіль «Робота».** «Warehouse», найімовірніше, — ваш Sklado (`pl.sklado.app`).
   Реальні пакети Warehouse і Scanner обираєте ви на телефоні з переліку встановлених програм (Етап 8).
   Наперед пакети в коді не прописуємо.

## 4. Технологічний стек

Kotlin, Jetpack Compose, MVVM + Repository, Coroutines/Flow, Room (профілі),
DataStore (дрібні налаштування), LauncherApps/PackageManager, Intent,
SpeechRecognizer, NotificationManager (політика DND), AudioManager.

Версії зафіксовані в `gradle/libs.versions.toml` та README. minSdk 26, targetSdk 36.
Жодних мережевих, рекламних чи аналітичних залежностей. Дозвіл `INTERNET` не оголошуємо.

## 5. Правила виконання (без змін)

1. Працювати тільки над поточним етапом.
2. Перед зміною коду перевіряти фактичний стан проєкту.
3. Не переписувати працюючі модулі без потреби.
4. Нові функції — тільки після погодження (див. розділ 9, Backlog).
5. Не переходити далі, якщо етап або блок не пройшов критерії приймання.
6. Після кожного етапу — зелена CI-збірка та тести.
7. Кожен етап — окремий коміт.
8. README та CHANGELOG оновлюються разом із поведінкою.
9. Помилку спочатку відтворити, знайти причину й тоді виправляти.
10. Обмеження Android фіксувати й пропонувати рішення в межах офіційних API.
11. «Компілюється» ≠ «готово».
12. Не заявляти про тестування, якого не було.

## 8. Ризики (з версії 1.0) і наші відповіді

| Ризик | Рішення |
|---|---|
| Видимість пакетів | `LauncherApps` + `<queries>` |
| Голос офлайн | перевіряємо `isOnDeviceRecognitionAvailable` (API 31+), не обіцяємо до перевірки |
| Звук у різних виробників | бажане ≠ фактичне, читаємо `ringerMode` після зміни |
| Вибіркове блокування сповіщень | тільки DND-політика; без NotificationListener у v1 |
| Втрата стану | Room + DataStore, відновлення в `onCreate` |
| Немає SDK/емулятора в хмарі (новий) | CI-збірка + ручна перевірка на телефоні блоками |
